# CLAUDE.md

Rules for working in this repo. See README.md for what LabelLens is, setup, commands and layout.
If a local PLAN.md exists, read it for phases, design notes and open questions (it is never pushed).

## Hard rules

- **Never commit.** When a chunk of work is ready for a commit, tell the user and suggest a
  conventional message (`feat:`, `fix:`, `docs:`, `test:`, `chore:`). The user commits.
- **Wording:** never use the word "safe" in user-facing text;
  never give dosing or treatment advice; missing info is missing, never good news. Every page shows
  "Research prediction, not medical advice"; results show "This checks the label, not what is
  inside the product". Tests enforce the "safe" ban (`frontend/src/i18n/i18n.test.ts`; backend
  verdict-string test arrives with the rules engine).
- **Colour:** never green or red for verdicts; always pair status colour with an icon and text.
- **Reference data:** never invent monograph content. Placeholder rows must have `verified=false`
  and a `TODO(expert)` note. Same for `plant_names`.
- **Extraction:** copy text verbatim, never infer values that aren't printed, `not_stated` when
  absent; every field has `value`, `status` (stated/not_stated/unreadable), `confidence`, `evidence`.
  Store `prompt_version`, provider and model with every extraction.
- **Rules engine** (`backend/app/rules`): pure Python, no FastAPI/SQLAlchemy imports, versioned,
  fully unit-tested, `TODO(expert)` where judgement is needed.
- **Pitch numbers** come only from `validation/run_validation.py` output.
- Ask before big decisions or new dependencies not in PLAN.md; otherwise decide and note the
  assumption in PLAN.md.
- If the design (docs/design/) conflicts with these rules, raise it; don't silently pick.

## Code and repo rules

- **New files only when needed.** Don't split code into extra files or abstractions "for
  reusability" unless the code is actually reused.
- **Minimal backend tests.** Test logic that must not break (auth, permissions, rules engine,
  extraction validation). No tests for small or trivial changes.
- **Short comments.** One or two lines at most, only where the code isn't self-explanatory. No
  long explanatory comments or docstrings.
- **Clean code, best practices.** Keep it simple and readable; follow the conventions below.
- **Performance matters.** Prefer the efficient solution: avoid N+1 queries, unnecessary
  re-renders, redundant requests and heavy dependencies.
- **Never push sensitive data.** Secrets, keys and passwords live only in `.env` (gitignored);
  `.env.example` keeps them empty. No password literals anywhere, not even fake ones in tests,
  compose defaults, CI or docs (GitGuardian flags them); generate test passwords at runtime.
- **What gets pushed:** code, config, `README.md` and `CLAUDE.md`. Not pushed: `PLAN.md`, the
  design (`docs/design/`), other docs (`docs/*.md`, `DATA_SOURCES.md`, `data/README.md`,
  `validation/README.md`) and `scripts/unpack_design.py`. Don't create new documentation files.

## Conventions

- API errors return `{"detail": "<code>"}` with stable codes (`invalid_credentials`,
  `email_taken`, `password_too_short`, `consent_required`, `invitation_invalid`,
  `too_many_requests`, `forbidden`, `not_authenticated`); the UI maps them to `error.<code>` keys.
- All datetimes are timezone-aware UTC (`UTCDateTime` column type rejects naive values).
- Tokens (share links, invitations): `secrets.token_urlsafe(32)`, store SHA-256 only, with expiry.
- Audit important actions with `services.audit.audit(...)`; never log passwords or tokens.
- Role guard: `Depends(require_roles(Role.admin, ...))` in the backend; `<RequireRole roles=[...]>`
  in the frontend. The backend is the real gate.
- The UI is English only. All user-facing text goes in `frontend/src/i18n/en.ts` and is read with
  `t("key")`; no hardcoded strings in components.
- Styling uses the design-token Tailwind classes (`bg-surface`, `text-muted`, `bg-match-bg`,
  `rounded-control`, ...) from `frontend/src/theme/tokens.css`; never hardcode colours or sizes.
- Migrations must not import app code (keeps old migrations runnable after refactors). Review
  autogenerated migrations and replace `app.*` types with plain `sa` types.
- Run lint, type checks and tests before saying work is ready to commit.
